# PDF 38–39: two-session lock experiments

These points are **Parte VIII**, not EXPLAIN/index points. No live server/client was available in this checkout. `src/parte_viii_session_a.sql` and `src/parte_viii_session_b.sql` are **manually coordinated snippets**, not scripts to source end-to-end. Never run on production: table locks block writers, even when no values change. Use a disposable InnoDB `hotel_db` copy, two independent connections, and an existing reservation ID. Confirm `SHOW TABLE STATUS LIKE 'reserva'` reports InnoDB and `SELECT @@autocommit` is 1 in B. If a step fails, execute `ROLLBACK; UNLOCK TABLES;` in A and close both connections; do not leave a transaction open.

## Procedure / predicted outcomes (not observations)

1. In A select a real `id_reserva`; replace the example `1` in **both** snippets with that ID. Verify A and B have different `CONNECTION_ID()` values. B sets session `lock_wait_timeout` and `innodb_lock_wait_timeout` to 10 seconds; these are upper bounds, not proof of waiting.
2. **P38 table:** A runs `LOCK TABLES reserva READ`, then pauses. B runs plain `SELECT` (should proceed), then the no-op `UPDATE` (should wait, possibly error 1205). While B is waiting A runs `UNLOCK TABLES`; record whether B completed or timed out, elapsed time and connection IDs. `LOCK TABLES` may implicitly commit an existing transaction: do not interleave with row-lock phase. B's autocommit update commits by itself.
3. **P38 row / P39 concurrency:** A starts a fresh transaction and `SELECT ... FOR UPDATE` on the chosen row; A pauses. B's nonlocking `SELECT` normally reads a committed version via MVCC; B's no-op `UPDATE` on the *same* row waits for A. A runs `ROLLBACK` before B's timeout if practical; record B's completion or error and duration. If B already timed out, retry its update only after A rolls back. Optionally demonstrate B's `SELECT ... FOR UPDATE` blocks as a locking read, one B statement at a time.
4. In both phases record connection IDs, engine/version, ID, A acquisition/release timestamps, B start/end timestamps, whether SELECT proceeded, error codes, and final row value. A no-op UPDATE still acquires an exclusive lock and may cause write-side activity; rollback avoids persistent row changes in A, but B autocommits a no-op statement. Do not assume no triggers/audit side effects: inspect schema first.

Table READ locks and InnoDB row locks are different mechanisms; a plain consistent SELECT does not imply it acquired a shared row lock. Test actual blocking under the selected isolation level; if the schema has triggers or the engine is not InnoDB, stop and redesign the experiment. A nonlocking read sees a snapshot, not necessarily A's uncommitted state. This is a reproducible protocol, **not** evidence that any wait or blocking was observed.
