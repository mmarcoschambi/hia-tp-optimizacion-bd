# PDF 38–39: two-session lock experiments

These points are **Parte VIII**, not EXPLAIN/index points. A local MariaDB 10.6 lab was explicitly authorized and tested using Python connector. `src/parte_viii_session_a.sql` and `src/parte_viii_session_b.sql` are **manually coordinated snippets**, not scripts to source end-to-end. Never run on production: table locks block writers, even when no values change. Use a disposable InnoDB `hotel_db` copy, two independent connections, and an existing reservation ID. Confirm `SHOW TABLE STATUS LIKE 'reserva'` reports InnoDB and explicitly set `SET SESSION autocommit = 1` in B before any UPDATE (the local Python connector was observed with `@@autocommit=0`). If a step fails, execute `ROLLBACK; UNLOCK TABLES;` in A and close both connections; do not leave a transaction open.

## Procedure / predicted outcomes (not observations)

1. In A select a real `id_reserva`; replace the example `1` in **both** snippets with that ID. Verify A and B have different `CONNECTION_ID()` values. B sets session `lock_wait_timeout` and `innodb_lock_wait_timeout` to 10 seconds; these are upper bounds, not proof of waiting.
2. **P38 table:** A runs `LOCK TABLES reserva READ`, then pauses. B runs plain `SELECT` (should proceed), then the no-op `UPDATE` (should wait, possibly error 1205). While B is waiting A runs `UNLOCK TABLES`; record whether B completed or timed out, elapsed time and connection IDs. `LOCK TABLES` may implicitly commit an existing transaction: do not interleave with row-lock phase. B's autocommit update commits by itself.
3. **P38 row / P39 concurrency:** A starts a fresh transaction and `SELECT ... FOR UPDATE` on the chosen row; A pauses. B's nonlocking `SELECT` normally reads a committed version via MVCC; B's no-op `UPDATE` on the *same* row waits for A. A runs `ROLLBACK` before B's timeout if practical; record B's completion or error and duration. If B already timed out, retry its update only after A rolls back. Optionally demonstrate B's `SELECT ... FOR UPDATE` blocks as a locking read, one B statement at a time.
4. In both phases record connection IDs, engine/version, ID, A acquisition/release timestamps, B start/end timestamps, whether SELECT proceeded, error codes, and final row value. A no-op UPDATE still acquires an exclusive lock and may cause write-side activity; rollback avoids persistent row changes in A, but B autocommits a no-op statement. Do not assume no triggers/audit side effects: inspect schema first.

Table READ locks and InnoDB row locks are different mechanisms; a plain consistent SELECT does not imply it acquired a shared row lock. Test actual blocking under the selected isolation level; if the schema has triggers or the engine is not InnoDB, stop and redesign the experiment. A nonlocking read sees a snapshot, not necessarily A's uncommitted state. ## Observed local lab run

`python src/run_parte_viii_lab.py --run` on MariaDB 10.6.23 / `hotel_db` (InnoDB), independent connection IDs **16 and 17**, `id_reserva=1`; B explicitly used autocommit=1. During A's `LOCK TABLES reserva READ`, B's plain SELECT succeeded, B's no-op UPDATE was still waiting at 1.5 seconds, then completed in **1.513 s** after A unlocked. During A's `SELECT ... FOR UPDATE` transaction, B's plain SELECT completed in **0.001 s**, while B's no-op UPDATE was still waiting at 1.5 seconds and completed in **1.503 s** after A rolled back. The row's `estado_reserva` matched its initial value at the end. These are single-run wall-clock observations, not performance distributions, and the in-progress flag is evidence of a blocked statement at the observation point (not a server-side lock trace). No timeout occurred. A released the table lock and rolled back the row transaction; B used autocommit for its no-op updates.

Repeat with `python src/run_parte_viii_lab.py --run` only on an authorized disposable lab. Offline guardrail: `python src/validate_parte_viii.py`.
